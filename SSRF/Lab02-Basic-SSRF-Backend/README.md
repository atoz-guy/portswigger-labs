# Lab 02: Basic SSRF Against Another Back-End System

**Platform:** PortSwigger Web Security Academy  
**Tool:** Burp Suite Community Edition  
**Vulnerability:** Server-Side Request Forgery (SSRF)  
**Vulnerable Feature:** Stock-check functionality  
**Level:** Apprentice  
**Lab Status:** Completed

**Goal:** Use the stock-check functionality to scan the internal `192.168.0.X` range for an administrative interface on port `8080`, then use it to delete the user `carlos`.

---

## 1. Understand

### What is SSRF?

Server-Side Request Forgery (SSRF) occurs when an attacker can influence the destination of a request that the application server makes. Because the request originates from the server, it can reach internal services that are not exposed to external users.

### Security Boundary

The application server sits inside a network that also contains back-end systems, such as an administrative interface, that external users cannot reach directly.

In this lab the administrative interface is not on the application server itself. It is on a separate internal host somewhere in the `192.168.0.0/24` range, listening on port `8080`. The vulnerability is that an external user can make the application server send requests across that boundary to any internal address.

### How This Differs From Lab 01

In Lab 01 the target was `localhost`, the application server itself. Here the target is a different back-end host whose address is not known in advance. The address has to be discovered first by scanning the internal range through the vulnerable feature.

## 3. Hypothesize

### Hypothesis H1

I hypothesized that the application server would fetch an attacker-supplied URL pointing at an internal address without validating the destination.

If correct, sending the fetch to each host in the `192.168.0.X` range would let me tell the hosts apart by their responses, and the host running the admin interface on port `8080` would respond differently from the empty addresses.

**Expected Result:** Most addresses return a connection-style error. The live admin host returns a different status, revealing which address to target.

**Hypothesis Status:** Not tested at the time of formulation.

## 4. Test and Record Evidence

Each observation below states only what the response established. A status code shows what it shows; on its own it does not identify which component produced it.

### Test 1: Manual Probes in Repeater

I sent the fetch to a few individual addresses to see how the endpoint behaved before automating.

| `stockApi` destination | Response | Note |
|---|---|---|
| `http://192.168.0.1:8080/` | `400 Bad Request` `"Missing parameter"` | Response did not identify which parameter or why. |
| `http://192.168.0.2:8080/` | `500 Internal Server Error` | Status alone did not establish the cause. |
| `http://192.168.0.3:8080/` | `500 Internal Server Error` | Same behavior as `.2`. |

Screenshots: `04-stockapi-0.1-missing-parameter.png`, `05-stockapi-0.2-500-error.png`, `07-stockapi-0.3-500-error.png`

**Observation:** Probing one address at a time is slow and does not scale across 255 hosts. This motivated automating the sweep.

### Test 2: Automated Sweep of the Internal Range (Intruder)

**Setup:**

1. Sent the stock-check request to Intruder.
2. Cleared the default payload positions (`Clear §`).
3. Marked the last octet of the internal address as the single payload position, using a Sniper attack.
4. Configured a numeric payload from `1` to `255`, step `1`.

Screenshots: `02-clear-intruder-positions.png`, `03-set-sniper-payload-position.png`, `06-intruder-sniper-setup.png`

**Result:**

Across the sweep, most addresses returned `500`, and some returned `400`. Request `109` stood out by returning `404 Not Found`, a different status from every other host, with a different response length.

Screenshot: `08-intruder-404-on-request-109.png`

**Evidence:** The distinct `404` on `192.168.0.109` indicated a host that was actually responding over HTTP, unlike the addresses that produced connection-style errors. This is the address the sweep was designed to surface.

### Test 3: Confirm the Live Host in Repeater

**Address root:** `http://192.168.0.109:8080/`

**Result:** `404 Not Found`. The host answered, but the root path returned nothing.

Screenshot: `09-stockapi-0.109-404.png`

**Admin path:** `stockApi=http://192.168.0.109:8080/admin`

**Result:**

```http
HTTP/2 200 OK
Content-Type: text/html; charset=utf-8
```

The `200 OK` on `/admin`, after the `404` at the root, confirmed that the application server had reached the internal administrative interface through the stock-check parameter.

Screenshot (highlighted): `11-stockapi-0.109-admin-200.png`

### Test 4: Confirm the Admin Interface Contents

Using the Render view on the `/admin` response showed the administrative page, including the user list and a Delete control for each user.

```text
Users
wiener - Delete
carlos - Delete
```

Screenshot (highlighted): `12-admin-users-list-rendered.png`

A direct request to `GET /admin` on `192.168.0.109:8080` returned `302 Found` with `Location: http://192.168.0.109:8080/admin`, consistent with the admin routing.

Screenshots: `10-admin-delete-302.png`, `13-direct-admin-302.png`

### Test 5: Trigger Unauthorized User Deletion

**Modified Parameter:**

```text
stockApi=http://192.168.0.109:8080/admin/delete?username=carlos
```

**Result:**

```http
HTTP/2 302 Found
Location: http://192.168.0.109:8080/admin
```

The `302` redirect back to the admin page matched the behavior of a completed delete action. Rendering the result confirmed it.

Screenshots: `14-admin-delete-carlos-302.png`, `15-user-deleted-solved.png`

```text
User deleted successfully!
Congratulations, you solved the lab!
```

The PortSwigger lab page then showed the Solved status.

Screenshot: `16-lab-solved.png`

**Hypothesis Status:** Supported.

## 5. Conclude and Reflect

### Technical Conclusion

The stock-check feature let a user-controlled URL drive requests from the application server into the internal network. By sweeping the `192.168.0.X` range I located an administrative host at `192.168.0.109:8080`, reached its `/admin` interface, and submitted a request that deleted a user.

### Root Cause

The application did not restrict the destination addresses supplied through the `stockApi` parameter. The server would fetch any internal address an external user chose, so the internal network became reachable from the outside through the application.

### Potential Risk

An attacker can use this to map and reach internal services that are not exposed to the internet, and to perform actions on them with the application server's network position. In this lab that meant unauthorized deletion of a user account. In a real environment the same weakness could expose internal admin panels, metadata services, or other back-end systems.

### Remediation

1. **Avoid user-controlled destination URLs:** Accept product and store identifiers instead of a full URL, and build the inventory request on the server.
2. **Allowlist destinations:** If a URL is required, restrict it to explicitly approved hosts, and validate the resolved address and any redirects.
3. **Restrict outbound access:** Prevent the application server from reaching internal ranges such as `192.168.0.0/24` and loopback addresses unless a request genuinely needs them (network segmentation).
4. **Enforce administrative authorization:** Require authentication and authorization for admin actions instead of relying on the request's network origin.

### Lessons Learned

- I learned to turn a single-host SSRF into a discovery problem: when the target address is unknown, the fetch itself becomes a scanner.
- I learned to read status codes as signals. A host that answers with `404` is behaving differently from one that returns a connection-style `500`, and that difference is what flagged `192.168.0.109`.
- I learned to confirm an automated hit by hand in Repeater before acting on it.
- I learned that the `200` on `/admin` and the rendered user list are the real proof that the trust boundary was crossed. The delete is the impact, not the finding.
- I learned to use Intruder's Sniper mode with a numeric payload to cover a full address range quickly.
